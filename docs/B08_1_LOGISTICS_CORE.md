# B08.1. Ядро территорий и графика погрузки

Статус: `реализовано и объединено с main; продолжение — B08.2`

B08.1 создает первый рабочий срез логистики на обезличенных данных. Реальные
названия, водители и машины не требуются для разработки и будут внесены
владельцем в B22.

На локальном B20 владелец упростил текущий административный интерфейс: водитель
сам выбирает постоянную территорию, а администратор видит территории, водителей
и группы погрузки. Формы машин, постоянных назначений, готовых рейсов и
дополнительного рейса скрыты. Серверная модель и история B08 не удаляются, чтобы
не переписывать подтверждённые операции и сохранить возможность вернуться к
детальному расписанию после пилота.

## Что реализовано

- девять территорий с постоянными номерами, редактируемыми названиями,
  архивированием и оптимистической версией;
- профили водителей только для активных сотрудников с ролью `DRIVER`;
- справочник машин с нормализованным уникальным госномером;
- версионируемые постоянные закрепления территории, водителя и машины;
- запрет пересекающихся периодов закрепления на уровне PostgreSQL;
- идемпотентное создание одного чернового рейса на активную территорию и дату;
- независимое назначение водителя, машины, времени и группы конкретному рейсу;
- группы погрузки и порядок от одного до четырех рейсов;
- запрет пересечения активных рейсов одного водителя или одной машины;
- публикация только полностью назначенных рейсов;
- неизменяемая история замен, общий аудит и transactional outbox;
- защищенный API с правами администратора, руководителя и кладовщика;
- адаптивный административный экран `/logistics` для справочников и графика;
- интеграционные тесты PostgreSQL на идемпотентность, публикацию и конфликт.
- самостоятельное начало и завершение водителем фактического рейса территории на московскую дату;
- только один активный водитель на территорию и только одна активная территория на водителя;
- последовательная смена без администратора: первый завершает рейс, второй после этого приступает;
- неизменяемые события начала и завершения, аудит и transactional outbox.

## Основные маршруты API

- `GET /api/v1/logistics/setup`;
- `PATCH /api/v1/logistics/territories/:id`;
- `POST/PATCH /api/v1/logistics/vehicles`;
- `PUT /api/v1/logistics/drivers/:employeeId`;
- `POST /api/v1/logistics/default-assignments`;
- `GET /api/v1/logistics/days/:date`;
- `POST /api/v1/logistics/days/:date/generate`;
- `POST /api/v1/logistics/groups`;
- `PATCH /api/v1/logistics/runs/:id/assignment`;
- `POST /api/v1/logistics/days/:date/publish`.
- `POST /api/v1/logistics/me/route/activate` — водитель приступил к рейсу;
- `POST /api/v1/logistics/me/route/:routeShiftId/end` — водитель закончил рейс.

Все изменяющие маршруты требуют серверную сессию, CSRF и роль администратора.
Чтение общего графика разрешено администратору, руководителю и кладовщику.

## Защита данных

- уникальность территории/даты/номера рейса обеспечивает БД;
- пересечения периодов и интервалов блокируются exclusion constraints;
- конкурентное создание дня сериализуется advisory lock;
- повторное создание дня не создает новые рейсы и повторный аудит;
- изменение рейса требует актуальную версию;
- опубликованный день повторно не создает уведомления;
- после начала погрузки назначение не изменяется этим API;
- подтвержденные операции не удаляются и не переписываются.
- второй водитель не может принудительно забрать активную территорию;
- смена водителя выполняется только после завершения первого рейса, поэтому одновременно активен один сотрудник.

## Что остается в B08.2

- отдельные представления «Сегодня» для водителя и планшета кладовщика;
- проверка открытой смены перед `READY_FOR_LOADING`;
- настраиваемый буфер между последовательными рейсами;
- блокировка пересекающихся интервалов одной физической зоны погрузки;
- второй рейс территории с обязательной причиной;
- календарное исключение территории 9 после появления B09;
- push-уведомления о публикации и замене;
- полная автоматизация A08-01–A08-22 и тесты целевых устройств.

## Проверка

Для локальной и CI-приемки обязательно:

1. применить все миграции дважды;
2. выполнить тест `logistics.repository.integration.spec.ts` с PostgreSQL;
3. выполнить `npm run check`;
4. собрать контейнеры API, worker и web;
5. проверить `/logistics` на ширине телефона, iPad и офисного экрана.

## Определение «готово» B08.1

- миграция применяется на чистой и обновляемой БД;
- девять черновиков создаются повторяемо без дублей;
- пересекающееся назначение отвергается PostgreSQL;
- полностью назначенный рейс публикуется вместе с группой;
- история замены и аудит сохраняются;
- web, API и тесты собираются без ошибок;
- рабочие данные фабрики не требуются и не попадают в репозиторий.
