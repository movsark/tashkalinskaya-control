# Эксплуатация, мониторинг и восстановление

Статус: проектное решение B04
Цели: RPO 0 для подтвержденных операций в принятой модели отказов, RTO до 4 часов

## 1. Ответственность

Владелец фабрики владеет аккаунтом Timeweb и управляет доступами. До
промышленного запуска назначаются:

- основной технический ответственный;
- заместитель на случай недоступности основного;
- получатель бизнес-тревог по плану, складу, погрузке и интеграциям;
- лицо, разрешающее восстановление или аварийный режим.

Назначения хранятся в закрытом операционном реестре, а не в публичной
документации.

## 2. Наблюдаемость

### Метрики

- доступность и время ответа web/API;
- доля ответов 5xx и ошибок авторизации;
- загрузка CPU, памяти и диска каждого узла;
- активные соединения, блокировки и задержка репликации PostgreSQL;
- глубина очереди и возраст самой старой задачи;
- время последнего успешного автоматического плана;
- время последней успешной резервной копии и WAL-архива;
- число неподтвержденных складских и погрузочных операций;
- число расхождений инвентаризации;
- успешность Web Push.

### Логи

Логи структурированы и содержат timestamp, окружение, версию, request ID,
тип события и обезличенный идентификатор пользователя. Запрещено писать
пароли, tokens, cookies, содержимое QR, персональные поля и фото.

Бизнес-аудит хранится отдельно от технических логов и не заменяется ими.

### Трассировка

Request ID проходит через web, API, worker и outbox. Для критической операции
по нему можно связать пользовательский запрос, commit БД и доставку
уведомления без раскрытия секрета.

## 3. Минимальные тревоги

| Событие | Срочность | Реакция |
|---|---|---|
| Приложение недоступно 2 минуты | критическая | немедленно |
| Primary БД недоступен или нет безопасного подтверждения записи | критическая | немедленно, блокировать рискованные записи |
| Реплика отстает сверх принятого порога | высокая | проверить кластер |
| Автоплан не завершен в установленное окно после 10:00 | критическая бизнес-тревога | администратор и техответственный |
| Очередь критичных задач старше 5 минут | высокая | проверить worker/outbox |
| Нет успешной резервной копии более 26 часов | критическая | восстановить резервирование |
| S3 или диск заполнен более чем на 80% | высокая | освободить/расширить |
| Рост 5xx выше базового порога | высокая | проверить текущий релиз |

Первичный канал рекомендуется Telegram-группа только для тревог, резервный —
телефонный звонок владельцу для критических событий. Финальный канал
фиксируется до пилота.

## 4. Резервные копии

- непрерывный архив WAL;
- ежедневная физическая копия PostgreSQL;
- еженедельная логическая контрольная выгрузка;
- версионирование и Object Lock для S3;
- зашифрованная копия вне основного production-контура;
- автоматическая ежедневная проверка наличия, размера, возраста и читаемости;
- ежемесячная выборочная проверка;
- квартальное полное тестовое восстановление;
- полное восстановление обязательно перед промышленным запуском.

Рекомендуемый срок хранения:

- ежедневные копии — 35 дней;
- еженедельные — 13 недель;
- ежемесячные — 12 месяцев;
- бизнес-аудит и подтвержденные операции — не менее года, затем по
  утвержденной политике хранения.

Сроки уточняются после проверки объема и требований бухгалтерии, но не могут
быть уменьшены без решения владельца.

## 5. Протокол тестового восстановления

1. Выбрать контрольную точку и записать ожидаемое время.
2. Создать изолированное окружение без доступа реальных сотрудников.
3. Восстановить БД, затем объекты S3 и конфигурацию соответствующей версии.
4. Проверить целостность миграций и отсутствие незавершенных транзакций.
5. Сверить контрольные количества производства, склада, погрузки, возврата и
   списания.
6. Выполнить вход всех ключевых ролей и чтение журнала действий.
7. Зафиксировать фактические RPO/RTO, ошибки и ответственных за исправление.
8. Уничтожить временные копии по правилам защищенных данных.

Проверка считается успешной только при документированном протоколе и RTO не
более четырех часов.

## 6. Runbook инцидента

1. Подтвердить событие и назначить руководителя инцидента.
2. Сохранить временную шкалу и request ID; не публиковать секреты в чате.
3. Остановить только операции, для которых нельзя гарантировать сохранность.
4. Выбрать: переключение узла, откат релиза или восстановление.
5. Сообщить пользователям, какие операции доступны и что нельзя повторять.
6. Восстановить сервис и сверить критические движения по аудиту.
7. Получить подтверждение владельца о возврате к штатной работе.
8. В течение двух рабочих дней оформить причину и предупреждающие меры.

Нельзя «чинить» расхождение прямым редактированием production-БД без
версионированной административной операции и записи в аудите.

## 7. Проверки до пилота

- тест отказа одного app-узла;
- тест потери соединения клиента после нажатия подтверждения;
- тест повторной отправки с тем же ключом идемпотентности;
- тест переключения БД;
- восстановление из копии в отдельное окружение;
- проверка доставки каждой критической тревоги;
- проверка отсутствия персональных данных и токенов в логах.
