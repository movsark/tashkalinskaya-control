## Обязательный staging-прогон до B21

Профиль `tests/load/factory-staging.example.json` моделирует 70 пользователей и
чтение табеля, производства, склада и контроля. Перед запуском:

1. загрузить обезличенный объём не меньше ожидаемого года;
2. включить staging-only read-доступ для синтетического администратора;
3. включить метрики двух app-узлов и трёх DB-узлов;
4. прогреть приложение пять минут;
5. выполнить профиль не менее трёх раз;
6. отдельно провести безопасные write-сценарии QR, производства и группы четырёх
   водителей на изолированной дате;
7. сохранить p50/p95/p99, ошибки, CPU, RAM, соединения БД, lock waits и размер очередей.

Команда read-профиля:

```bash
LOAD_BASE_URL=https://staging.example \
LOAD_BUSINESS_DATE=2030-01-15 \
LOAD_READ_TOKEN='<только локально>' \
node scripts/load-test.mjs --run tests/load/factory-staging.example.json
```

Исходный ключ хранится только в GitHub Environment, а Timeweb получает лишь его
SHA-256 отпечаток. Доступ работает только при `NODE_ENV=staging`, требует
активную фабричную роль администратора или руководителя и отклоняет любые
изменяющие HTTP-запросы до бизнес-логики. Секреты и полный ответ API в отчёт не
записываются.

После создания GitHub Environment `staging` тот же профиль запускается вручную
workflow `Staging gates`; порядок описан в [runbook B20.2](B20_2_STAGING_RUNBOOK.md).

## Первый авторизованный прогон B20.3

04.08.2026 версия `519bf2a6658711e088db51499e444d1e2d97cba7` прошла
public smoke 7/7 и приняла отдельный read-only ключ. Прогон 70 пользователей,
1 400 запросов завершился неуспешно: error rate 46,6%, p50 765,220 мс,
p95 3 005,100 мс, p99 3 043,622 мс. Причины разделены на две группы:

- профиль ошибочно передавал `productionDate` вместо поддерживаемого `date`,
  поэтому производственный экран отвечал HTTP 400;
- технический тайм-аут 3 секунды обрывал медленные ответы и не позволял увидеть
  их фактическое распределение.

Этот запуск не засчитывается как приемочный. Исправленный профиль сохраняет
целевой порог p95 не выше 1 секунды, использует тайм-аут 10 секунд только для
полноты измерений и публикует отдельные метрики каждого вида запроса.

## Диагностика платформы и БД на версии 1b30612

04.08.2026 версия `1b3061240d6e616b81c3f90d80febd35562aed7d` снача прошла
внешний smoke 7/7. Затем один и тот же запуск сравнил рабочие экраны
с двумя контрольными endpoint-ами под 70 одновременными пользователями:

| Контур | p50 | p95 | Ошибки | Порог p95 ≤ 1 с |
|---|---:|---:|---:|---|
| API liveness без БД | 532,350 мс | 901,451 мс | 0 из 350 | пройден |
| API readiness с БД | 543,238 мс | 913,107 мс | 0 из 350 | пройден |
| Четыре рабочих экрана | 620,809 мс | 1 591,390 мс | 0 из 1 400 | не пройден |

Readiness с обращением к PostgreSQL почти не отличается от liveness без БД.
Значит, покупать второй app-узел или расширять кластер БД по этому результату
не нужно. Задержка возникает при массовом повторе одинаковых бизнес-чтений.

Следующее точечное изменение: одинаковые одновременные чтения табеля,
производства, склада и контрольного экрана объединяются в один запрос к БД.
Объединение живёт только до завершения текущего запроса. Готовый ответ не
кэшируется, поэтому следующее чтение сразу видит новую запись. Операции записи,
журнал и подтверждения не кэшируются и не изменяются.

Покупка второго app-узла или расширение БД по этим данным автоматически не
выполняется. Следующий инфраструктурный эксперимент требует отдельного решения
владельца о платных ресурсах. До него B20 продолжает recovery drill, ролевой UAT
и полевые сценарии устройств; все подтверждённые операции остаются вне кэша.
