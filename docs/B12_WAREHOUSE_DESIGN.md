# B12. Приёмка готовой продукции и складские остатки

Статус: проектные решения приняты; операционное ядро B12.1 реализовано

Связанные документы:

## 1. Цель и границы

B12 делает физическую приёмку кладовщиком единственной точкой появления
готовой продукции на складе и вводит воспроизводимый складской журнал.

Блок должен:

- показать кладовщику партии B11, ожидающие физической проверки;
- принять полностью, принять частично либо отклонить партию;
- создать отдельное расхождение при любой разнице;
- увеличить склад ровно один раз только на принятое количество;
- хранить неизменяемые движения и вычисляемые остатки;
- запрещать отрицательный остаток;
- исправлять подтверждённый факт только компенсирующим документом;
- дать трассировку от партии до движения и текущего остатка;
- подготовить единый складской фундамент для планирования, магазина,
  погрузки, возврата, списания и инвентаризации.

За рамками B12:

- погрузка водителю — B13;
- ежедневный физический пересчёт — B14;
- годный возврат — B15;
- порча и списание — B16;
- сырьё, упаковка, рецептуры и полуфабрикаты;
- адресное хранение по стеллажам, холодильникам и ячейкам;
- уникальный серийный учёт каждой коробки;
- остаток фирменного магазина после передачи.

## 2. Основные термины

- **Заявлено** — количество неизменяемой партии B11.
- **Принято** — физически проверенное кладовщиком количество.
- **Расхождение приёмки** — разница между заявленным и принятым.
- **Очередь** — партии `AWAITING_WAREHOUSE`; это ещё не складской остаток.
- **Свободный остаток** — подтверждённый товар без активного резерва.
- **Корзина** — логическое состояние количества в складском журнале.
- **Движение** — неизменяемая проводка между двумя корзинами.
- **Документ движения** — атомарное основание одной или нескольких проводок.
- **Проекция остатка** — быстрый итог журнала, который можно пересчитать.

## 3. Роли и полномочия

| Действие | Кладовщик | Ответственный цеха | Администратор | Руководитель |
|---|---:|---:|---:|---:|
| Смотреть очередь | да | партии своего цеха | да | сводка |
| Начать проверку | да | нет | да | нет |
| Принять/отклонить | да | нет | да | нет |
| Комментировать расхождение | да | да, свой цех | да | нет |
| Закрыть расхождение | нет | нет | да | нет |
| Смотреть свободный остаток | да | чтение нужного среза | да | да |
| Создать корректировку | нет | нет | да | нет |
| Применить корректировку | нет | нет | да | нет |
| Смотреть журнал движений | да | только связанные партии | да | да |

Один администратор может применить корректировку согласно D-10. Обязательны
причина, неизменяемый аудит и уведомление руководителю.

## 4. Решения W12-01–W12-18

### W12-01. Единая очередь приёмки

Статус: `Принято`

В очередь попадают только партии B11 со статусом `AWAITING_WAREHOUSE`:

- подтверждённый сверхплан должен уже иметь решение;
- отозванные, заменённые и отклонённые партии не показываются активными;
- очередь сортируется по приоритету ночной партии, сроку и времени заявления;
- доступны фильтры по цеху, товару, смене и производственной дате;
- на карточке видны заявленное количество, автор, цех, время и связь с
  исправленной партией;
- штрихкод определяет вид товара, но не отдельную коробку.

Количество на коробках кладовщик пересчитывает физически и вводит общей
цифрой — поштучное сканирование в MVP не требуется.

### W12-02. Захват партии на проверку

Статус: `Принято по рекомендации`

Перед вводом результата кладовщик переводит партию:

```text
AWAITING_WAREHOUSE → IN_REVIEW
```

Система сохраняет кладовщика и серверное время. Другой кладовщик видит, кто
проверяет партию, и не может одновременно завершить её. Администратор может
снять зависший захват с причиной. Автоматическое истечение захвата возвращает
партию в очередь только если решения ещё нет, и фиксируется в аудите.

### W12-03. Один финальный результат на партию

Статус: `Принято`

У партии ровно один актуальный терминальный результат:

```text
IN_REVIEW → ACCEPTED
          ↘ PARTIALLY_ACCEPTED
          ↘ REJECTED
```

- `ACCEPTED` — принято всё заявленное количество;
- `PARTIALLY_ACCEPTED` — принято от 1 до `declared - 1`;
- `REJECTED` — принято 0.

`WarehouseReceipt` неизменяем и содержит заявленное, принятое, отклонённое,
причину разницы, кладовщика, серверное время, бизнес-дату и idempotency key.

### W12-04. Частичная приёмка

Статус: `Принято по рекомендации`

Частичная приёмка разрешена, потому что физический факт может отличаться от
заявления цеха.

- кладовщик вводит фактически принятое целое количество;
- система сама рассчитывает отклонённую часть;
- причина и комментарий обязательны;
- принятое количество атомарно переходит в `FREE_STOCK`;
- непринятая часть переходит в виртуальную корзину `REJECTED_RECEIPT`;
- автоматически создаётся `ReceiptDiscrepancy`;
- исходная партия больше не открывается для повторной приёмки;
- если цех фактически донёс недостающее, он создаёт новую связанную партию B11.

### W12-05. Полное отклонение

Статус: `Принято по рекомендации`

При принятом количестве 0:

- причина и комментарий обязательны;
- вся партия переводится из `PENDING_RECEIPT` в `REJECTED_RECEIPT`;
- `FREE_STOCK` не меняется;
- создаётся расхождение на всё количество;
- ответственный цеха получает уведомление и создаёт исправленную партию при
  необходимости.

Повторно открыть отклонённую партию нельзя.

### W12-06. Фактически больше заявленного

Статус: `Принято по рекомендации`

Под одной партией нельзя принять больше заявленного:

- кладовщик принимает максимум заявленное;
- лишнее количество остаётся физически отдельно до оформления цехом новой
  партии;
- если итог производства выше плана, применяется правило сверхплана B11;
- административная корректировка не используется как быстрый способ обойти
  оформление партии.

Так сохраняется связь каждого принятого количества с производственным фактом.

### W12-07. Расхождение приёмки

Статус: `Принято по рекомендации`

`ReceiptDiscrepancy` создаётся автоматически при частичной приёмке или
отклонении и хранит:

- партию и документ приёмки;
- заявленное, принятое и разницу;
- код причины и комментарий кладовщика;
- состояние;
- комментарий ответственного цеха;
- решение администратора;
- связанные исправленные партии или корректировки.

Состояния:

```text
OPEN → WORKSHOP_EXPLAINED → RESOLVED
    ↘ RESOLVED_BY_ADMIN
```

Ответственный цеха объясняет разницу. Администратор закрывает её:

- `EXPLAINED_NO_STOCK_CHANGE`;
- `REPLACEMENT_BATCH_RECEIVED`;
- `ADMIN_CORRECTION_APPLIED`;
- `DOCUMENTED_LOSS`;
- `OTHER` с обязательным комментарием.

Закрытие расхождения само по себе не меняет склад.

### W12-08. Корзины B12

Статус: `Принято`

В B12 используются:

- `PENDING_RECEIPT` — виртуально заявлено цехом, ещё не склад;
- `FREE_STOCK` — свободный физически принятый товар;
- `REJECTED_RECEIPT` — виртуальная терминальная корзина непринятого;
- `RESERVED_FOR_LOADING` — резерв B13;
- `RESERVED_FOR_STORE` — резерв выдачи B10;
- `RETURN_POOL` — годный возврат B15;
- `BLOCKED_FOR_WRITEOFF` — заблокировано B16;
- `WRITTEN_OFF` — терминально списано;
- `PRODUCTION_DEFECT` — подтверждённый производственный брак;
- `ADJUSTMENT_CLEARING` — техническая балансирующая сторона корректировки.

`PENDING_RECEIPT`, `REJECTED_RECEIPT`, `PRODUCTION_DEFECT` и
`ADJUSTMENT_CLEARING` не входят в физический остаток склада.

### W12-09. Неизменяемый журнал движений

Статус: `Принято`

Каждая подтверждённая операция создаёт один `StockMovementDocument` и одну или
несколько строк `StockMovement`.

Строка содержит:

- товар;
- исходную и целевую корзину;
- целое положительное количество;
- бизнес-дату;
- серверное время;
- документ-основание;
- автора и активную роль;
- correlation ID.

Строки после фиксации не обновляются и не удаляются. Документ либо целиком
записывается одной транзакцией, либо не записывается совсем.

### W12-10. Атомарная приёмка

Статус: `Принято`

Одна серверная транзакция:

1. блокирует партию и проверяет её версию;
2. проверяет полномочия и idempotency key;
3. создаёт `WarehouseReceipt`;
4. создаёт документ движения;
5. переводит принятое в `FREE_STOCK`;
6. переводит остаток в `REJECTED_RECEIPT`;
7. обновляет проекцию остатков;
8. создаёт расхождение и audit/outbox-события;
9. фиксирует терминальный статус партии.

Сбой любого шага откатывает всю транзакцию. Повтор команды возвращает
сохранённый результат.

### W12-11. Свободный и физический остаток

Статус: `Принято`

Для товара:

```text
free_stock = balance(FREE_STOCK)

warehouse_on_hand =
    FREE_STOCK
  + RESERVED_FOR_LOADING
  + RESERVED_FOR_STORE
  + RETURN_POOL
  + BLOCKED_FOR_WRITEOFF
```

Терминальные и виртуальные корзины в `warehouse_on_hand` не входят.

План B09 получает только явно выбранный подтверждённый источник и не считает
`PENDING_RECEIPT` доступным остатком.

### W12-12. Проекция и источник истины

Статус: `Принято`

`StockMovement` — источник истины. `StockBalance` — производная проекция для
быстрого интерфейса.

- уникальная строка проекции: товар + корзина + логический склад;
- проекция обновляется в транзакции с движением;
- контрольная задача пересчитывает итог из журнала;
- несовпадение блокирует критичные новые списания затронутого товара и создаёт
  тревогу;
- исправление проекции не создаёт бизнес-движение и не меняет журнал;
- отчёт «на момент времени» строится по движениям до выбранного timestamp.

### W12-13. Один логический склад в MVP

Статус: `Принято по рекомендации`

В MVP используется один активный объект `Warehouse` с кодом
`MAIN_WAREHOUSE`.

- холодильники, помещения, стеллажи и ячейки не ведутся;
- перемещения между физическими зонами не создаются;
- схема хранит `warehouse_id`, чтобы добавить площадки в будущем;
- интерфейс не просит кладовщика выбирать склад;
- пилот проверяет, достаточно ли одного логического остатка.

### W12-14. Запрет отрицательного остатка

Статус: `Принято`

Временный отрицательный остаток запрещён во всех окружениях и корзинах,
которые представляют доступный или физический товар.

- команда блокирует строки проекции в устойчивом порядке;
- проверяет доступное количество внутри транзакции;
- при недостатке возвращает актуальный остаток и не создаёт частичный документ;
- параллельные резервы/списания сериализуются;
- исправление отрицательного остатка задним числом не является допустимым
  рабочим процессом.

### W12-15. Резервы

Статус: `Принято по рекомендации`

Резерв — подтверждённое движение из `FREE_STOCK` в целевую резервную корзину:

- магазин — `RESERVED_FOR_STORE`;
- погрузка — `RESERVED_FOR_LOADING`;
- резерв не меняет `warehouse_on_hand`, но уменьшает `free_stock`;
- резерв имеет бизнес-документ, срок и владельца;
- отмена резерва создаёт обратное движение;
- истечение не удаляет запись и не освобождает товар без движения;
- один и тот же товар нельзя зарезервировать дважды.

Полные сценарии резерва завершаются в B10/B13, но фундамент создаётся в B12.

### W12-16. Административная корректировка

Статус: `Принято по рекомендации и D-10`

Подтверждённое движение не редактируется. `StockCorrection` создаёт новый
документ между нужной корзиной и `ADJUSTMENT_CLEARING`.

Обязательны:

- товар, корзина и целое количество;
- направление увеличения/уменьшения;
- код причины и комментарий;
- ссылка на исправляемый документ, если он известен;
- автор, серверное время и idempotency key;
- уведомление руководителю.

Перед применением показываются остаток до и после. Уменьшение не может сделать
остаток отрицательным. Ошибочная корректировка исправляется следующей обратной
корректировкой, а не удалением.

### W12-17. Онлайн-режим, конкуренция и сохранность

Статус: `Принято`

- приёмка и корректировка выполняются только онлайн;
- без серверного ответа приложение показывает `Операция не подтверждена`;
- локальный черновик результата не влияет на очередь и остатки;
- клиент отправляет idempotency key и ожидаемую версию партии;
- повтор после потери ответа безопасен;
- подтверждённые документы не удаляются при синхронизации и восстановлении;
- резервная копия включает журнал, документы, проекции, аудит и связи с
  партиями;
- проверка восстановления пересчитывает проекции из журнала.

### W12-18. Уведомления, контроль и наблюдаемость

Статус: `Принято по рекомендации`

Контролируются:

- партия слишком долго ожидает приёмки;
- ночная партия просрочила утренний срок;
- партия принята частично или отклонена;
- расхождение ждёт объяснения/решения;
- повторная или конфликтующая команда;
- недостаточный остаток;
- проекция не совпадает с журналом;
- применена административная корректировка.

Технические метрики:

- длина и возраст очереди;
- время приёмки;
- доля частичных/отклонённых партий;
- число конфликтов и повторов;
- задержка outbox;
- число несовпадений проекции;
- длительность контрольного пересчёта.

Push не является источником истины: событие всегда остаётся на контрольном
экране.

## 5. Экранные контракты

### 5.1. Очередь кладовщика

- крупные карточки для iPad;
- товар, цех, заявлено, производственная дата и время ожидания;
- ночной приоритет и просрочка;
- фильтр и поиск/сканирование штрихкода вида товара;
- индикатор, если партию проверяет другой кладовщик;
- отдельные группы `Ожидает`, `На проверке`, `Расхождение`, `Завершено`.

### 5.2. Карточка приёмки

- неизменяемое заявленное количество;
- крупный ввод принятого количества;
- быстрые действия `Принять всё`, `Принято меньше`, `Отклонить`;
- причина и комментарий при разнице;
- понятный итог движения до подтверждения;
- одна финальная кнопка с защитой от повторного нажатия.

### 5.3. Остатки

- товар, свободно, в резервах, возврат, блокировка и всего физически;
- время актуальности проекции;
- раскрытие до документов движений;
- поиск по коду, названию и штрихкоду;
- предупреждение о расхождении проекции;
- без кнопки прямого редактирования числа.

### 5.4. Расхождения и корректировки

- очередь открытых расхождений;
- комментарии склада и цеха;
- связанная партия, приёмка и движение;
- решение администратора;
- предварительный остаток до/после корректировки;
- история без удаления записей.

## 6. Справочники начальных данных

Перед staging подтверждаются:

- название единственного логического склада;
- причины частичной приёмки и отклонения;
- причины административной корректировки;
- сроки обычной и ночной очереди;
- роли конкретных кладовщиков;
- технические лимиты количества и фото/комментариев;
- кто получает уведомления о критичных корректировках.

Справочники причин версионируются. Архивирование причины не меняет прошлые
документы.

## 7. Контрольные запросы

Для каждого товара система должна уметь доказать:

```text
projection(product, bucket)
  = sum(incoming movements)
  - sum(outgoing movements)
```

И отдельно:

```text
declared production
  = accepted to FREE_STOCK
  + rejected to REJECTED_RECEIPT
```

для каждой терминально обработанной партии.

Контрольные выборки:

- партия без результата приёмки;
- партия с двумя успешными результатами;
- receipt без документа движения;
- документ без сбалансированных строк;
- движение без бизнес-основания;
- отрицательная проекция;
- сумма проекции, не совпадающая с журналом;
- открытое расхождение без ответственного/срока;
- корректировка без причины или уведомления.

## 8. Порядок реализации

Последовательно:

1. B11 создаёт неизменяемые партии;
2. B12 реализует очередь, захват и решение;
3. документ движения и проекция обновляются одной транзакцией;
4. остатки подключаются к B09/B10;
5. резервы подключаются к B13;
6. B15 проверяет физический остаток;
7. B15/B16 добавляют возврат и списание на тот же журнал.

Параллельно после утверждения журнала можно разрабатывать:

- очередь и карточку приёмки;
- экран остатков;
- реестр расхождений;
- контрольные запросы и мониторинг;
- административную корректировку.

## 9. Риски и меры

| Риск | Мера |
|---|---|
| Двойная приёмка после повторного клика | уникальный receipt и idempotency key |
| Частично принятое потеряло остаток | две атомарные проводки в одном документе |
| Число остатка исправили вручную | нет прямого редактирования, только correction |
| Параллельное списание дало минус | блокировка строк и проверка в транзакции |
| Расхождение осталось без решения | ответственный, срок и эскалация |
| Ожидающая партия вошла в план | виртуальная корзина исключена из склада |
| Проекция разошлась с журналом | контрольный пересчёт и блокировка операции |
| Слишком сложный учёт зон | один логический склад в MVP |
| Корректировка скрыла ошибку процесса | ссылка на основание и уведомление руководителю |

## 10. Оценка трудоёмкости

Блок крупный:

- очередь, конкурентная приёмка и расхождения — несколько недель;
- журнал движений, проекции и корректировки — несколько недель;
- интеграция с B09–B11, контрольные запросы и пилот — ещё несколько недель.

Диапазон уточняется после технического каркаса БД и нагрузочной проверки
конкурирующих движений. Это оценка объёма, а не точная календарная дата.

## 11. Определение «готово»

Проектная часть B12 готова, когда приняты W12-01–W12-18 и приемочные сценарии.

Реализация готова, когда:

- очередь показывает все допустимые партии B11;
- полная, частичная приёмка и отклонение атомарны;
- повтор не создаёт второй receipt или движение;
- любая разница создаёт отдельное расхождение;
- склад увеличивается только на принятое;
- свободный остаток полностью объясняется журналом;
- отрицательный остаток невозможен;
- корректировка не меняет прошлую запись;
- проекция восстанавливается из движений;
- ролевые, конкурентные, интеграционные и восстановительные тесты проходят;
- пилот «все цехи + склад» принят владельцем фабрики.
