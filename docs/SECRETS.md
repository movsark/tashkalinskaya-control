# Политика секретов и доступов

Статус: проектное решение B04

## 1. Что считается секретом

- пароли и строки подключения к БД/Redis;
- ключи подписи сессий, QR и API;
- pepper одноразовых кодов `AUTH_TOKEN_PEPPER`;
- pepper серверных сессий `SESSION_TOKEN_PEPPER`;
- ключ CSRF `CSRF_SECRET`;
- приватные ключи Web Push;
- токены GitHub, Timeweb, S3 и мониторинга;
- ключи шифрования резервных копий;
- учетные данные SMTP или внешних интеграций;
- аварийные коды и recovery-ключи.

Production-данные, фотографии брака, табель и резервные копии не являются
«настройками»: это защищаемые рабочие данные, которые также запрещено хранить
в Git.

## 2. Где хранить

| Область | Хранилище |
|---|---|
| Local | локальный `.env`, не попадающий в Git |
| CI | GitHub Actions secrets/environments |
| Staging | отдельные секреты окружения Timeweb |
| Production | отдельные секреты окружения Timeweb с ограниченным доступом |
| Резервные копии | отдельный ключ шифрования вне основного production-контура |
| Аварийный доступ | защищенный менеджер паролей владельца, с MFA |

В репозиторий добавляется только `.env.example` без реальных значений после
появления конфигурации приложения.

## 3. Доступы

- владелец фабрики является владельцем аккаунтов GitHub и Timeweb;
- для повседневной работы создаются персональные учетные записи;
- MFA обязательно для GitHub, Timeweb, домена и хранилища резервных копий;
- production-доступ получают только владелец и назначенный технический
  ответственный;
- доступ подрядчика ограничивается сроком и отзывается после завершения работ;
- общие логины запрещены;
- изменение прав и аварийный вход фиксируются в журнале.

## 4. Жизненный цикл

Секрет создается отдельно для каждого окружения и получает владельца.
Ротация выполняется:

- немедленно при подозрении на утечку или уходе ответственного;
- после аварийного доступа;
- для внешних токенов — не реже одного раза в год;
- для долгоживущих ключей подписи — по утвержденной процедуре с периодом
  одновременного принятия старого и нового ключа.

Ротация не должна принудительно завершать незаконченные подтвержденные операции.

## 5. Проверка перед merge

- в diff нет `.env`, ключей, токенов и персональных выгрузок;
- примеры содержат заведомо фиктивные значения;
- логи не печатают заголовки авторизации, cookies, QR-токены и строки
  подключения;
- секрет не вшит в клиентский PWA;
- при обнаружении секрета его удаление из последнего commit недостаточно:
  секрет сразу отзывается и создается новый.
