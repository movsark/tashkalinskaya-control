# B20. Протокол проверки восстановления

Цели: RPO 0 для подтверждённых операций в утверждённой синхронной модели,
RTO не более 4 часов. Протокол выполняется на staging и затем повторяется перед
production. B20.1 подготовил процедуру, B20.2 добавил исполняемый контрольный
manifest; фактический результат на Timeweb ещё не получен.

## Участники

- руководитель учения — владелец аккаунта Timeweb;
- исполнитель инфраструктуры;
- администратор приложения;
- кладовщик или владелец контрольных складских данных;
- наблюдатель, который фиксирует время и доказательства.

## Подготовка

1. Зафиксировать версию приложения, миграции и checksum образов.
2. Создать контрольные операции: выпуск, приёмку, погрузку, возврат, списание и табель.
3. Сохранить их UUID, audit correlation ID и контрольные суммы отчётов.
4. Остановить worker и меняющий трафик, создать baseline командой
   `npm run test:recovery:capture -- --output var/recovery/baseline.json`.
5. Проверить наличие полной резервной копии, WAL/журнала и отдельного доступа к секретам.
6. Убедиться, что учение не затрагивает production.

## Сценарий

1. `T0`: объявить отказ и запретить меняющие запросы через ingress.
2. Зафиксировать последний подтверждённый correlation ID и состояние DB-кластера.
3. Восстановить БД в новый изолированный кластер из backup + журнала.
4. Применить только штатные миграции; ручные SQL-исправления запрещены.
5. Поднять один API и один worker без внешнего трафика.
6. Выполнить readiness и сверку количества audit/outbox/движений.
7. Выполнить `npm run test:recovery:verify -- --input var/recovery/baseline.json`
   против восстановленного кластера.
8. Пересчитать `stock_balance` из ledger и сравнить без расхождений.
9. Проверить контрольные UUID, отчёты, фото-метаданные и активные роли.
10. Поднять второй app-узел, выполнить smoke и ролевой вход.
11. `T1`: открыть тестовый ingress и зафиксировать фактический RTO/RPO.
12. Удалить временные секреты и закрыть изолированное окружение после подписания.

## Условие успеха

- все контрольные подтверждённые операции присутствуют ровно один раз;
- ledger и balance совпадают;
- миграции имеют ожидаемые checksum;
- очередь возобновляет обработку без дублей;
- нет доступа старым отозванным сессиям;
- RPO = 0, RTO ≤ 4 часа;
- протокол подписан владельцем Timeweb и владельцем данных.

При невыполнении любого пункта запуск B21 блокируется. В журнал дефектов вносятся
время, причина, потерянный диапазон, ответственный и повторная дата учения.
