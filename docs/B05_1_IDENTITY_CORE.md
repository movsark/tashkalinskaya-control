# B05.1. Ядро авторизации и сотрудников

Статус: реализовано и объединено в `main`; продолжение — B05.2

## 1. Назначение

B05.1 — первый функциональный программный срез. Он реализует безопасную основу
для персонального доступа, но не объявляет весь B05 завершённым.

В срез входят:

- создание первого персонального администратора через контролируемую CLI-команду;
- приглашение сотрудника администратором через одноразовый текстовый код с заранее выбранной
  должностью и областью;
- девять ролей MVP и области доступа;
- самостоятельное заполнение ФИО, логина и пароля только после сканирования
  одноразового QR сроком 24 часа;
- парольная фраза и Argon2id;
- вход по логину и паролю с любого личного устройства;
- серверная сессия в `HttpOnly`, `SameSite=Strict` cookie;
- CSRF и проверка Origin для изменяющих запросов;
- распределённое ограничение попыток входа через PostgreSQL;
- блокировка, увольнение, архив и немедленный отзыв доступа;
- запрет отключения последнего активного администратора;
- неизменяемый аудит операций доступа.

## 2. Интерфейсы

- `/login` — вход по логину и паролю с любого устройства;
- `/activate` — первый вход и создание локального неэкспортируемого ключа;
- `/register` — упрощённая регистрация по одноразовому коду администратора;
- `/employees` — список сотрудников и создание учетной записи;
- `/api/docs` — OpenAPI.

Стартовый экран B04.1 обновлён и ведёт в рабочий контур B05.

## 3. API

Публичные операции:

- `POST /api/v1/auth/activate`;
- `POST /api/v1/auth/register/preview`;
- `POST /api/v1/auth/register`;
- `POST /api/v1/auth/login`.

Операции с сессией:

- `GET /api/v1/auth/session`;
- `POST /api/v1/auth/logout`.

Административные операции:

- `GET /api/v1/employees`;
- `GET /api/v1/employees/invitations/options`;
- `POST /api/v1/employees/invitations`;
- `POST /api/v1/employees`;
- `PATCH /api/v1/employees/:employeeId/status`;
- `PUT /api/v1/employees/:employeeId/roles`;
- `POST /api/v1/employees/devices/:deviceId/revoke`.

Скрытая кнопка не считается защитой. Каждый административный endpoint повторно
проверяет действующую сессию, роль, область фабрики и CSRF.

## 4. PostgreSQL

Миграция `0002_identity_foundation.sql` создаёт:

- `identity.employee`;
- `identity.user_account`;
- `identity.role` и `identity.role_assignment`;
- `identity.personal_device`;
- `identity.factory_terminal`;
- `identity.access_token`;
- `identity.session`;
- `identity.login_rate_limit`;
- справочник подразделений.

Миграция `0028_employee_qr_invitations.sql` добавляет одноразовые приглашения без
хранения исходного QR-кода. Должность и область фиксируются до регистрации;
приглашение и создание сотрудника попадают в аудит.

База данных допускает несколько активных технических записей устройств сотрудника,
чтобы парольный вход работал в Safari, установленной PWA и на другом телефоне. Каждая
сессия остаётся отдельной. Аудит защищён триггерами от `UPDATE` и `DELETE`.

## 5. Первый администратор

До запуска web/API применяются миграции. Затем в защищённом терминале
задаются переменные:

- `DATABASE_URL`;
- `DATABASE_SSL`;
- `AUTH_TOKEN_PEPPER`;
- `BOOTSTRAP_ADMIN_FULL_NAME`;
- `BOOTSTRAP_ADMIN_LOGIN`;
- `BOOTSTRAP_ADMIN_PERSONNEL_NUMBER`.

Команда:

```bash
npm run bootstrap:admin -w @tashkalinskaya/api
```

Команда работает только пока в системе нет администратора. Она показывает
одноразовый код ровно один раз. Код передаётся лично, не копируется в тикет,
чат или журнал. При желании оператор заранее задаёт
`BOOTSTRAP_ADMIN_ACTIVATION_CODE` через защищённый secret input.

## 6. Защита секретов

- пароль хранится только как PHC-строка Argon2id;
- activation/session token хранится как HMAC-хеш с отдельным pepper;
- PIN не передаётся и не хранится;
- сырые коды, cookie и полный публичный ключ не записываются в аудит;
- неизвестный логин, неверный пароль и заблокированный аккаунт получают один
  ответ;
- после пяти ошибок растёт задержка, после десяти действует временная
  блокировка;
- отзыв сессии применяется к следующему запросу.

Local-значения `.env.example` непригодны для staging/production. Три секрета
должны генерироваться независимо и храниться в Timeweb.

## 7. Проверка

На отдельной локальной PostgreSQL выполнено:

1. две миграции на чистой БД;
2. повторный запуск мигратора;
3. создание первого администратора;
4. активация и установка cookie;
5. восстановление сессии;
6. создание сотрудника и выдача одноразового кода;
7. отказ изменяющего запроса без CSRF;
8. запрет блокировки последнего администратора;
9. выход и отказ старой сессии.

CI дополнительно запускает интеграционный тест частичного уникального индекса
устройства и собирает три контейнерных образа.

## 8. Продолжение B05.2

WebAuthn challenge, системный PIN/биометрия, recovery, замена устройства,
выход из всех сессий, step-up и pairing фабричного терминала реализованы в
[B05_2_DEVICE_SECURITY.md](B05_2_DEVICE_SECURITY.md).

До полной приемки B05 остаются полевая проверка A05-01–A05-15 на реальных
Samsung, iPhone и iPad, назначение двух администраторов пилота и ролевые
сценарии конкретных цехов, которые завершаются вместе с B06.

## 9. Определение «готово» для B05.1

- миграция дважды проходит на чистом PostgreSQL;
- первый администратор создаётся без hardcoded-пароля;
- сотрудник регистрируется только по одноразовому коду администратора;
- новый браузер может войти по правильным логину и паролю без предварительной привязки;
- пароль использует Argon2id;
- cookie имеет `HttpOnly` и `SameSite=Strict`, а в TLS-окружениях — `Secure`;
- сервер запрещает административную операцию без роли/CSRF;
- последний администратор защищён;
- отзыв сессии немедленный;
- web/API/worker собираются и CI зелёный.
