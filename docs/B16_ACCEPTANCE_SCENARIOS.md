# B16. Приёмочные сценарии

## Автоматизированное ядро

- **A16-01:** запрос из `RETURN_POOL` блокирует только доступное количество.
- **A16-02:** повтор команды создания не создаёт второй запрос или движение.
- **A16-03:** параллельные запросы не уводят остаток пула в минус.
- **A16-04:** физическая порча требует корректного источника.
- **A16-05:** кладовщик не может утвердить или отклонить запрос.
- **A16-06:** утверждение перемещает блок в `WRITTEN_OFF` ровно один раз.
- **A16-07:** отклонение запроса из пула возвращает количество в `RETURN_POOL`.
- **A16-08:** отклонение физической порчи исключает её из складского остатка.
- **A16-09:** решение нельзя повторить с другим результатом.
- **A16-10:** причина с `photo_required=true` блокирует запрос без фото.
- **A16-11:** сервер отклоняет файл больше 10 МБ и неподдерживаемый реальный тип.
- **A16-12:** допустимое фото нормализуется, не получает публичного URL и связано с запросом.
- **A16-13:** внешний номер сохраняется без попытки автоматической интеграции.
- **A16-14:** ручную сверку выполняет только администратор.
- **A16-15:** `MISMATCH` требует комментарий, повтор сверки сохраняет новую ревизию.
- **A16-16:** очередь, реестр и складской баланс показывают один и тот же статус.
- **A16-17:** подтверждённые решения и ревизии сверки нельзя изменить или удалить.
- **A16-18:** аудит и outbox фиксируются в одной транзакции с движением.

## Полевые сценарии B21

- **A16-19:** кладовщик фотографирует повреждённый возврат на Samsung/iPhone.
- **A16-20:** администратор принимает решение с офисного компьютера.
- **A16-21:** порча от водителя и магазина принимается в одном рабочем дне.
- **A16-22:** администратор вручную сравнивает реестр с документом 1С/Agent Plus.
- **A16-23:** после утверждения списания ежедневная инвентаризация сходится.
