# B20. Стратегия тестирования MVP

Статус: автоматическая основа B20.1 реализована; Timeweb staging B20.2 развёрнут
и прошёл публичный smoke 02.08.2026. Авторизованная нагрузка, устранение сетевого
риска БД, физические устройства, восстановление, независимая проверка и UAT
остаются воротами перед пилотом B21.

## 1. Цель

Доказать не только работу отдельных экранов, но и сохранность подтверждённых
операций, ролевые ограничения, сходимость складского журнала, устойчивость к
повторам и возможность восстановить систему.

Порядок приоритетов:

1. отсутствие потери или скрытой правки подтверждённых операций;
2. отсутствие доступа за пределами роли и области;
3. правильные балансы, статусы и встречные подтверждения;
4. воспроизводимость после повтора, конкуренции и сбоя;
5. приемлемое время операции на целевых устройствах;
6. удобство и визуальная точность.

## 2. Уровни проверки

| Уровень | Что доказывает | Когда запускается |
|---|---|---|
| Модульный | формулы, парсеры, криптография, состояния | каждый PR |
| PostgreSQL-интеграционный | транзакции, блокировки, идемпотентность, журнал | каждый PR в CI |
| Контрактный | единые типы, коды и примеры обмена | каждый PR |
| Ролевой | закрыто по умолчанию, CSRF, роли, один привязанный телефон | каждый PR |
| Browser E2E | production API стартует, web/PWA работают, ключевые сценарии доступны | каждый PR |
| Нагрузочный | 70 пользователей и параллельные рабочие группы | локальный baseline; затем staging |
| Безопасность | доступ, заголовки, origin, загрузки, QR, аудит, зависимости | каждый PR + staging |
| Восстановление | RPO/RTO и пригодность резервной копии | staging перед B21 |
| UAT | процесс подходит фабрике | по ступеням B21 |

## 3. Обязательные ворота PR

PR нельзя объединять, если не прошли:

- проверка чувствительных файлов и локальных ссылок;
- Prettier, ESLint и TypeScript;
- unit и PostgreSQL integration tests;
- production build API, worker и web;
- `npm audit --omit=dev --audit-level=high`;
- применение миграций дважды на чистой PostgreSQL 18;
- пятнадцать Playwright-сценариев Chromium, включая мобильные роли и потерю связи;
- сборка контейнеров API, web и worker.

Access-policy test автоматически обнаруживает каждый route контроллеров. Новый
метод без утверждённой публичной церемонии, аутентификации, CSRF или ролей ломает
CI. Отдельная регрессия не допускает возврата повторного запроса входа после
действующей личной сессии.

## 5. Принятые пороги B20

До измерения staging действуют консервативные проектные пороги:

- обычное чтение: p95 не более 1 секунды;
- подтверждаемая команда: p95 не более 2 секунд;
- локальный технический baseline: p95 не более 500 мс, ошибок 0%;
- staging read-профиль: 70 пользователей, p95 не более 1 секунды, ошибок не более 1%;
- отрицательный остаток, дубль подтверждённой операции и чужой ролевой доступ — 0;
- RTO до 4 часов;
- RPO подтверждённых операций — 0 в утверждённой модели синхронного кластера.

Порог не считается доказанным production-результатом, пока тест не выполнен на
выбранном тарифе Timeweb, с сетевой задержкой и объёмом данных пилота.

## 6. Классификация дефектов

| Уровень | Определение | Выпуск |
|---|---|---|
| P0 критический | потеря/подмена данных, обход доступа, неверный баланс, приложение не стартует | немедленная остановка |
| P1 высокий | блокирует основную операцию смены, безопасного обхода нет | пилот запрещён |
| P2 средний | операция возможна с документированным обходом | решение до расширения пилота |
| P3 низкий | текст, внешний вид или редкий некритичный случай | допускается в backlog |

Для B21 не допускаются открытые P0/P1. P2 принимается только письменным решением
владельца процесса с временным обходом и сроком исправления.

## 7. Ответственные за приёмку

- владелец фабрики подписывает общий UAT и переход между ступенями;
- бухгалтер подписывает табель;
- ответственный цеха — производство и причины;
- кладовщик — приёмку, остатки, погрузку, возврат и порчу;
- основной водитель — нормы, рейс и встречное подтверждение;
- продавец — заказ магазина;
- администратор — доступы, справочники и технические процедуры;
- разработчик предоставляет доказательства, но не подписывает UAT вместо фабрики.

## 8. Команды

```bash
bash scripts/check-repository.sh
npm run test:e2e
npm run test:load:validate
STAGING_BASE_URL=https://staging.example EXPECTED_APP_VERSION=<sha> npm run test:staging:smoke
LOAD_BASE_URL=http://127.0.0.1:4180 node scripts/load-test.mjs --run tests/load/local-70-read.json
```

Staging-профиль требует `LOAD_BASE_URL`, `LOAD_BUSINESS_DATE` и отдельную тестовую
`LOAD_SESSION_COOKIE`. Значения не сохраняются в репозитории и не выводятся в
отчёт.

Развёртывание, GitHub Environment и recovery-команды описаны в
[runbook B20.2](B20_2_STAGING_RUNBOOK.md).
