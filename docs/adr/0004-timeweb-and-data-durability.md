# ADR-0004. Timeweb и сохранность подтвержденных операций

- Статус: принято, обязательная инфраструктурная проверка до production
- Дата: 30.07.2026
- Связанные решения: A-01, A-12, A-15

## Решение

Production размещается в российских зонах Timeweb Cloud. Предпочтительная основная локация — Санкт-Петербург, где доступно S3-хранилище.

Подтвержденная пользователю операция имеет целевой RPO 0:

1. API открывает транзакцию PostgreSQL.
2. Бизнес-изменение, аудит и outbox записываются в одной транзакции.
3. Успех возвращается только после локального commit и синхронного подтверждения минимум одной второй копией БД.
4. WAL непрерывно архивируется в приватное хранилище.
5. Ежедневно создается физическая резервная копия.
6. Копия резервных данных хранится отдельно от основного контура.
7. Восстановление регулярно проверяется на практике.

Документированная репликация Timeweb DBaaS для PostgreSQL асинхронная. Поэтому до production необходимо либо получить подтвержденную синхронную конфигурацию от Timeweb, либо развернуть собственный PostgreSQL-кластер в нескольких зонах доступности. Обычный одиночный DBaaS-кластер не считается достаточным для требования RPO 0.

Фото хранятся в приватном S3 Timeweb с версионированием/Object Lock, ограниченными ссылками и сроком оперативного хранения один год.

Владелец утвердил бюджет минимум на три узла PostgreSQL и два узла приложения. Владельцем аккаунта Timeweb и ответственным за управление доступами является владелец фабрики. Технический исполнитель восстановления назначается в инфраструктурном блоке B04.

## Последствия

Инфраструктура дороже одиночного сервера и требует ответственного за восстановление. Это осознанная стоимость требования не терять подтвержденные операции.
