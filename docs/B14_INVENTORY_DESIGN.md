# B14. Ежедневная инвентаризация и поиск расхождений

Статус: проектные решения приняты по ранее согласованному правилу «везде по рекомендации».

## Цель и границы

B14 фиксирует ежедневный физический пересчёт после погрузки, сохраняет неизменяемый
расчётный снимок и передаёт подтверждённый остаток в план производства после 10:00.

В MVP считаются готовые товары основного склада без серийного и адресного учёта.
Возвраты и списания подключаются к диагностике полностью в B15–B16, но их складские
корзины уже входят в расчёт.

## Решения I14-01–I14-14

1. На бизнес-дату действует одна текущая версия пересчёта. Поздний повторный пересчёт
   создаёт новую версию, предыдущая не удаляется.
2. Пересчёт открывает кладовщик или администратор. Повторную версию открывает только
   администратор с обязательной причиной.
3. В момент открытия фиксируются количества по физическим корзинам и хеш снимка.
4. Во время пересчёта склад не блокируется. Все движения после снимка показываются
   отдельным предупреждением и не меняют снимок незаметно.
5. Несколько кладовщиков могут заполнять разные товары. Для каждой строки сохраняются
   автор, время и версия; конфликт обновления требует перезагрузки.
6. Сканирование штрихкода выбирает вид товара. Количество вводится общей цифрой.
7. Отправка разрешена только после заполнения всех строк. Нулевая позиция вводится явно.
8. Подтверждённая отправка неизменяема и идемпотентна.
9. Разница считается как `факт − расчёт`. Любая ненулевая разница создаёт расхождение.
10. Критическое расхождение: модуль разницы не меньше 5 штук либо не меньше 5% расчёта.
11. Нулевой пересчёт закрывается автоматически. Ненулевые расхождения закрывает
    администратор объяснением либо компенсирующей складской проводкой.
12. Второй подтверждающий сотрудник в MVP не требуется. Аудит хранит всех участников.
13. План использует последнюю отправленную текущую версию за дату. Доступный свободный
    остаток определяется из физического факта за вычетом зафиксированных резервов,
    возврата и заблокированного товара.
14. Если пересчёт не отправлен, план использует текущий системный `FREE_STOCK` и добавляет
    предупреждение `INVENTORY_NOT_CONFIRMED`.

## Роли

| Действие | Кладовщик | Администратор | Руководитель |
|---|---:|---:|---:|
| Открыть первый пересчёт | да | да | нет |
| Вводить факт | да | да | нет |
| Отправить пересчёт | да | да | нет |
| Открыть позднюю версию | нет | да | нет |
| Закрыть ненулевое расхождение | нет | да | нет |
| Смотреть реестр и диагностику | да | да | да |

## Состояния

```text
DRAFT → SUBMITTED → RESOLVED
```

`SUBMITTED` без расхождений сразу становится `RESOLVED`. При наличии расхождений
сессия остаётся `SUBMITTED`, пока администратор не закроет все строки.

## Диагностика

Для товара показываются движения между предыдущим подтверждённым пересчётом и новым
снимком, сгруппированные по типу документа: приёмка, резерв, завершение погрузки,
корректировка, а в следующих блоках — возврат и списание. Движения после открытия
показываются отдельным счётчиком.

## Критерии готовности

- снимок и все отправленные версии воспроизводимы;
- частичный ввод не теряется, конкурентная перезапись отклоняется;
- факт, расчёт и разница видны по каждому товару;
- корректировка возможна только администратору, с причиной и проводкой;
- план различает подтверждённый пересчёт и системный fallback;
- аудит и outbox создаются в одной транзакции с операцией;
- эталонные сценарии проходят на чистой PostgreSQL.
