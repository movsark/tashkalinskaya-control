# Правила работы с репозиторием

Этот документ задает обязательный путь изменения системы от задачи до
попадания в `main`.

## 1. Основная ветка

- `main` содержит только проверенное состояние проекта;
- прямые push в `main` запрещены;
- изменение попадает в `main` только через pull request;
- предпочтительный способ объединения — squash merge;
- force push и переписывание истории `main` запрещены;
- каждый merge в `main` должен иметь зеленые обязательные проверки.

В настройках GitHub для `main` включаются ruleset/branch protection:

1. pull request обязателен;
2. требуется минимум одно одобрение владельца или назначенного
   ответственного;
3. новые коммиты сбрасывают старое одобрение;
4. обсуждения review должны быть закрыты;
5. обязательна проверка `Repository checks / validate`;
6. удаление ветки и force push запрещены.

До появления второго технического участника владелец фабрики утверждает
функциональные и эксплуатационные решения, а автор изменения не считает
собственную проверку заменой приемке владельцем.

## 2. Ветки и задачи

Одна ветка решает одну ограниченную задачу:

- `codex/b05-auth-foundation`;
- `codex/b07-attendance-qr`;
- `codex/fix-loading-confirmation`;
- `codex/docs-operations`.

Имя должно содержать блок дорожной карты или понятную область. Большую работу
нужно делить так, чтобы pull request можно было проверить без скрытых
побочных изменений.

## 3. Коммиты

Рекомендуемый формат:

```text
<тип>: <краткий результат>
```

Типы: `feat`, `fix`, `docs`, `test`, `chore`, `refactor`, `security`.

Примеры:

```text
docs: establish production recovery policy
feat: add employee device enrollment
fix: prevent duplicate warehouse acceptance
```

Нельзя добавлять в коммит секреты, реальные резервные копии, production-фото,
персональные выгрузки и рабочие файлы импорта.

## 4. Pull request

Pull request открывается как draft после появления проверяемого каркаса.
Перед переводом в готовый статус автор обязан:

1. связать изменение с блоком дорожной карты и сценарием приемки;
2. описать миграции, риски и способ отката;
3. выполнить локальные проверки;
4. проверить интерфейс на целевых размерах, если он менялся;
5. обновить документацию и журнал решений;
6. не включать несвязанные изменения.

Merge разрешен после зеленого CI, обязательного review и закрытия обсуждений.

## 5. Локальная проверка

Пока приложение не создано, базовая команда:

```bash
bash scripts/check-repository.sh
```

После появления приложения эта команда остается единой точкой входа и будет
дополнена форматированием, линтерами, проверкой типов, миграций, модульными и
интеграционными тестами.

## 6. Версии и релизы

- до пилота используются версии `0.x`;
- кандидат на staging помечается тегом `v0.x.y-rc.N`;
- принятый production-релиз помечается тегом `v0.x.y`;
- тег ставится только на commit из `main`;
- развертывается один и тот же неизменяемый образ, сначала на staging, затем
  на production;
- production не собирается вручную на сервере.

## 7. Миграции базы данных

- миграции версионируются вместе с кодом;
- уже примененная миграция не редактируется;
- миграция проверяется на пустой БД и на копии предыдущей схемы;
- опасное удаление поля делается минимум в два релиза;
- для каждой миграции описываются время блокировки, резервная копия и откат;
- несовместимая миграция не запускается одновременно на всех узлах приложения.

## 8. Аварийные изменения

Срочное исправление также проходит через короткую ветку и pull request.
Обход проверок допустим только при подтвержденном инциденте владельцем
production-доступа. После такого выпуска в течение следующего рабочего дня
обязательны обычный review, тесты и запись в журнале инцидента.
